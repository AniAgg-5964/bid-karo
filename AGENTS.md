## Product context
BidPilot AI is an AI-assisted tender discovery, eligibility, and compliance workflow. The planned MVP proves one official tender source end to end: discover/fetch with TinyFish, collect documents, extract source-cited requirements, compare them against a company profile and evidence library, then produce a fit report and compliance checklist.

## Non-negotiable domain rules
- Every requirement shown to a user needs source document, page (viewer and printed page if they differ), clause/form reference when available, verbatim excerpt, and source URL plus retrieval time. If it cannot be verified, mark it Unverified / partial / conflicting; never fabricate citations, requirements, authorities, deadlines, or consequences.
- Keep mandatory eligibility (`Pass` / `Fail` / `Unknown`) separate from the soft fit score. Unknown or missing evidence is never a pass, and a high score must not hide a failed mandatory criterion.
- Checklist items must be tender-specific: exact document/action, acceptance criteria, issuer/signatory, evidence checks, deadline or trigger, and consequence only when the source states it. No generic filler such as "check legal requirements".
- Do not assume standard requirements (notarization, stamp paper, affidavit, licence, validity period); extract each from the actual tender.
- TinyFish is the required web discovery/extraction integration and should do real work on a real source. Manual PDF upload is only a fallback for blocked sources.
- Use deterministic code for scoring, date normalization, deduplication, schema validation, and citation checks. Treat model output as untrusted until validated.
- The product supports decisions; it must not claim legal eligibility or submit bids autonomously.

## Implemented shape
Main orchestrator plus Discovery (TinyFish), Extraction, Analysis, Compliance, and Monitoring components, backed by deterministic validation and persistence. Persist tenders, documents, requirements, evidence matches, checklist tasks, and change snapshots with provenance. Built as a modular monolith (`routes -> services -> repositories -> MongoDB`) with company-scoped queries.

- Discovery: `app/integrations/tinyfish.py` (REST `GET /v1/search`, `POST /v1/fetch`, header `X-API-Key`), `services/discovery_service.py` (query building, prequalify, batched fetch, store, qualify), `services/tender_extraction.py` (deterministic fields, source type, dedupe, listing detection, listing-table rows), `services/relevance.py` (profile fit with reasons), `repositories/discovery.py`, routes under `/api/discovery` (`status`, `run`, `runs`, `sources`, `tenders`, `tenders/{id}`, `save`, `dismiss`).
- Tender documents and OCR: `services/pdf_extraction.py` (PyMuPDF text, viewer page index, printed label, bounded OCR fallback, `no_text_layer`), `services/ocr.py` (English Tesseract via `pytesseract`/`Pillow`, page render, timeout and failure reporting), `services/download.py` (public-host/size/magic-byte checks, redirect re-validation), `services/requirement_service.py` (upload dedupe by SHA-256, page persistence, chunking, per-item Pydantic validation, citation checks, review), `repositories/tender_documents.py`, routes in `api/routes/tender_documents.py`.
- AI: `integrations/ai.py` exposes a provider interface with Groq (`openai/gpt-oss-120b` default, JSON mode, bounded retries on 429/5xx) and Gemini. Output is untrusted; each item is validated individually so one bad item cannot sink a chunk.
- Tender document routes: `GET/POST /api/tenders/{id}/documents`, `POST /api/tenders/{id}/documents/fetch`, `GET/DELETE /api/tender-documents/{id}`, `GET .../pages`, `GET .../pages/{page}`, `GET .../download`, `POST .../extract`, `GET /api/tenders/{id}/requirements`, `GET .../requirements/summary`, `GET/PATCH /api/requirements/{id}`.
- Citation rules: a requirement is `verified` only when its normalized excerpt is found on the cited page of the same document. A match found only in OCR text is stored `needs_review`, not `verified`. Otherwise it is stored `unverified` with a reason. `needs_review` and `rejected` are human states and are audited. Re-running extraction skips duplicates; `replace=true` deletes AI-origin requirements for that document first.
- Auth/OTP: `services/email.py` (Gmail SMTP), `services/auth_service.py` (register challenge, password login, verify/resend, security toggle), `repositories/otp.py` (HMAC-hashed codes, expiry, cooldown, attempts, TTL index), `models/auth.py`, routes `POST /api/auth/register|login|verify-otp|resend-otp|security`.
- Phase 4 assessment: `services/assessment.py` (deterministic score, gate, deterministic evidence suggestions, checklist/legal selection), `repositories/assessment.py` (`evidence_matches`, `fit_assessments`), `models/assessment.py`, routes in `api/routes/assessment.py`: `GET /api/tenders/{id}/assessment`, `GET/POST /api/tenders/{id}/requirements/{rid}/evidence`, `GET /api/tenders/{id}/legal`, `GET /api/tenders/{id}/checklist`, `POST /api/tenders/{id}/checklist/generate`, `PATCH /api/checklist/{task_id}`.
- Retrieval (Qdrant): `services/vector_store.py` is the only place that talks to Qdrant; `services/embeddings.py` holds the embedding provider (the dimension comes from the provider, never from a constant); `services/chunking.py` makes passages that stay verbatim spans of their page; `services/document_ingestion.py` indexes the stored documents; `services/document_lifecycle.py` removes a deleted document's passages and marks the documents that need a rebuild after a model change; `services/retrieval.py` is the only way into the index; `services/citations.py` turns a passage into a source reference and checks it against the page.
- Retrieval rules: Qdrant is an index, not a source of truth. The documents, the requirements, the evidence decisions and the eligibility results stay in MongoDB and on disk, so the collection can be wiped and rebuilt. The company filter is always applied and comes from the authenticated user, never from the request; a scope only decides what a search may see inside that company. A passage is checked against the page it names, and one that is not found there is reported as unverified. Indexing is idempotent: the point id is derived from the document, the content hash and the chunk index, and a changed document has its old passages removed first. A failed run is recorded with its reason and never leaves a document marked as indexed. A store that is not available is reported, never faked.
- Retrieval knobs: `QDRANT_ENABLED`, `QDRANT_URL` (`http://127.0.0.1:6333`), `QDRANT_API_KEY`, `QDRANT_COLLECTION_NAME` (`bidkaro_knowledge`), `QDRANT_TIMEOUT_SECONDS` (10), `QDRANT_VECTOR_SIZE` (0 = the provider's own), `EMBEDDING_PROVIDER` (`model2vec`, the local semantic model, or `hashing`, the no-download fallback), `EMBEDDING_MODEL`, `EMBEDDING_DIMENSION` (0 = the provider's own), `EMBEDDING_BATCH_SIZE` (32), `CHUNK_MAX_CHARS` (1200), `CHUNK_OVERLAP_CHARS` (150), `CHUNK_MAX_PER_DOCUMENT` (2000), `RETRIEVAL_TOP_K` (8), `RETRIEVAL_MIN_SCORE` (0).
- Config knobs: `TINYFISH_API_KEY`, `TINYFISH_BASE_URL`, `DISCOVERY_MAX_CANDIDATES` (20), `DISCOVERY_FETCH_LIMIT` (12, capped at 10 per fetch), `DISCOVERY_MIN_SCORE` (0.3), `DISCOVERY_CACHE_HOURS` (24).
- Email/OTP knobs: `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME` (`bidkaroindia@gmail.com`), `SMTP_APP_PASSWORD` (Google App Password; required for live sending), `SMTP_FROM_NAME`, `SMTP_TIMEOUT_SECONDS`, `OTP_EXPIRE_MINUTES` (10), `OTP_RESEND_COOLDOWN_SECONDS` (60), `OTP_MAX_SENDS_PER_HOUR` (5), `OTP_MAX_ATTEMPTS` (5).
- OCR knobs: `OCR_ENABLED` (true), `OCR_LANGUAGE` (`eng`), `OCR_DPI` (300), `OCR_MAX_PAGES` (40), `OCR_TIMEOUT_SECONDS` (45), optional `TESSERACT_CMD`.
- AI/PDF knobs: `AI_PROVIDER`, `GROQ_API_KEY`, `GROQ_MODEL`, `GROQ_BASE_URL`, `GEMINI_API_KEY`, `GEMINI_MODEL`, `GEMINI_BASE_URL`, `AI_MAX_OUTPUT_TOKENS` (2000), `AI_REQUEST_TIMEOUT_SECONDS` (60), `PDF_MAX_PAGES` (200), `AI_EXTRACTION_MAX_CHUNK_CHARS` (4000), `AI_EXTRACTION_MAX_PAGES_PER_CHUNK` (3), `AI_EXTRACTION_MAX_CHUNKS` (12), `AI_EXTRACTION_MAX_PAGES` (80).
- Discovery rules: a run needs at least one sector/product/keyword in the company profile (else 422); a missing key returns 503. Only individual, still-open tenders are listed: a deadline or reference must be extracted, index/award pages are excluded, and past deadlines are dropped. Portal/index pages are stored, shown separately (`GET /api/discovery/sources`) and never listed as tenders. Dated tables on listing pages are parsed into individual tenders (`extracted_from: listing_table`). Social hosts are blocked before scoring. Relevance is profile fit only, never eligibility. Date-only deadlines are anchored at noon UTC so the calendar day survives IST display.
- Discovery matching rules (Phase 5 rework): a tender is listed when (a) it names one piece of work, (b) the work matches the company's services, sectors or keywords, (c) a closing date was read and it is still in the future, and (d) the notice is an Indian one. The region only decides the order, never the visibility. Profile terms are matched as plain text with deterministic variants (plural form, "B of A" word order) and every match is explained in `relevance.reasons`. A bare keyword hit needs a region match as well, so an ambiguous acronym such as "AMC" cannot list a tender on its own.
- Discovery reading rules: a closing date is read from a labelled closing/submission word, and a date labelled publish/open is never used as the closing date. Unlabelled table rows use the latest date in the row. Headerless tables are read positionally. A search result that describes one work becomes a tender even when the page it points at is a category page (`extracted_from: search_result`). Pages that name an authority but no work are not tenders. Sources are typed as `official_portal`, `authority` or `aggregator`, and every candidate is counted with the reason it was not listed.
- Assessment rules: score is 25% profile fit + 20% citation verification + 40% confirmed mandatory evidence coverage + 15% tender document readiness. Eligibility is separate; `pass` needs a verified citation plus human-confirmed non-expired evidence, `fail` needs a confirmed contradiction, otherwise `unknown`. Evidence suggestions never auto-pass. Checklist generation selects mandatory/submission/compliance/form-referenced requirements, is idempotent and preserves human status/owner.
- Workflow rules: `services/workflow.py` captures snapshots of normalized tender fields plus requirement fingerprints (no PDF copies); the content hash covers both, human review status is excluded from diffs, and a failed TinyFish recheck reports the error without fabricating a change. `services/reminders.py` derives reminders from deadlines and dated tasks, reopens them when the due date changes, and never sends email without explicit opt-in and `SMTP_APP_PASSWORD`. `services/calendar.py` emits authenticated, tenant-scoped ICS only (no Google Calendar OAuth). `api/routes/workflow.py` exposes changes, snapshots, refresh, reminders and both ICS downloads. `scripts/send-reminders.py` is the cron-able email job (dry-run by default, exit 2 without SMTP). Post-award obligations are cited performance/contract requirements; pre-award tasks and post-award obligations stay separate, and old tasks without `phase` are treated as `pre_award`.
- Tender packages: a tender may be uploaded as the ZIP it was published as. `services/package_extraction.py` reads the archive under fixed limits (path traversal refused, per-member and total expanded size, compression ratio, member count, one nesting level, executables never stored) and every refused member is reported with its reason. The archive is kept as a container document (`kind: package`); each stored file becomes its own document with `parent_document_id` and `archive_path`, so requirements cite the file they came from. PDFs are read as before, images become a one-page OCR document, and other formats are stored and marked "not parsed". Config: `PACKAGE_MAX_UPLOAD_MB` (200), `PACKAGE_MAX_MEMBERS` (200), `PACKAGE_MAX_MEMBER_MB` (25), `PACKAGE_MAX_EXPANDED_MB` (500), `PACKAGE_MAX_RATIO` (200), `PACKAGE_MAX_NESTING` (1).
- Agent architecture: `services/agents/gate.py` is the deterministic gate. The quote rule set checks that a quote exists on the page it was cited from (whitespace and typography insensitive); the grounding rule set checks that a recommendation refers only to clauses that passed the gate and introduces no figure that is not already in those clauses, in the tender record or in our own evidence. A sentence carrying an unsupported figure is removed and the rest of the advice is kept; the removed figure is listed. No model is called in the gate, and a failed check keeps the item with its reason.
- The three agents: `services/agents/recommender.py` (Agent 1) proposes the next step for each clause; `services/agents/verifier.py` (Agent 2) explains the deterministic eligibility verdict and proposes the next step, and may not change the verdict; `services/agents/legal_researcher.py` (Agent 3) reads official legal sources with TinyFish and quotes them. The model proposes, the gate disposes, a human confirms. Agent 1 and 2 write to the `recommendations` collection with an `origin` so a re-run of one does not delete the other; Agent 3 writes to `legal_sources`.
- Legal sources: `services/agents/sources.py` holds the allow-list (the central official domains), the topic map (which source answers which question) and the instrument map (which Act governs a clause). The research search names the instrument and the government domain, the result is filtered to the allow-list, and a law firm blog, a news site, a tender portal or an aggregator is refused rather than warned about. A state government domain is allowed only for the state-specific topics. When the official page cannot be read in a form that states the provision, the page we did read is cited with its date and the gap is stated; nothing is invented.
- The tender page has a **Recommend** tab: the analysis job with its steps, the proposals that passed the gate (with what to do, how we will know it is done, a suggested owner and a computed due date), the proposals that did not pass with their reason, and the official sources under each clause on the **Legal & contract** tab. A grounded proposal can be turned into a checklist task by a human.
- `services/job_runner.py` and the `jobs` collection run the analysis pipeline as steps with visible state: `requirements`, `recommendations`, `verification` and `legal_research`. A step that raises fails the job with the error; a step with no implementation reports "not available yet". Agents propose, the gate disposes, humans confirm.

## Open decisions
Stack, frontend language (JavaScript, not TypeScript), database, web-automation vendor (TinyFish) and the AI provider (Groq, configurable through `AI_PROVIDER`) are decided and locked. Groq's `llama-3.3-70b-versatile` was retired; the default is now `openai/gpt-oss-120b` after checking Groq's live model list. Still open: the first officially prioritised tender source beyond TinyFish's general web results, and hosting. Calendar integration is decided as ICS export only, with no Google Calendar OAuth. Phases 2-6 are implemented and verified for local review. Atlas is supported through `MONGODB_URI`; local files remain on disk. Live verification currently uses local MongoDB because Atlas DNS was unavailable.
